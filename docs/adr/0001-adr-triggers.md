# ADR-0001: 何时必须写 ADR

**状态：** Accepted
**日期：** 2026-08-04

## Context

仓库挖掘数据显示，约 50% 使用 ADR 的仓库只有 1–5 条记录，即「试了就放弃」。已知的失败模式一致：没有定义触发条件、评审人、存放位置。`[预印本/案例研究，确切出处待补]`

ECSA 2024 的 action research（Ahmeti, Linder, Wohlrab，[10.1007/978-3-031-70797-1_22](https://doi.org/10.1007/978-3-031-70797-1_22)）在一家微服务公司引入 ADR 观察三个月，团队认为有用，但明确指出「文档太多或太少都有风险，从业者想要清晰的指引」。`[同行评审]`

因此第一条 ADR 定义 ADR 自身的触发规则。

## Decision

### 必须写 ADR 的触发条件

命中任一即 MUST 写：

1. 引入或移除一个外部协议、依赖或服务
2. 改变信任边界或数据流向
3. 改变模块边界或部署单元
4. **改变开源/闭源的划线**
5. 否决了一个曾被认真考虑的方案
6. 一个决定在六个月后会有人问「当初为什么这么定」

### 不需要写

命名 · 格式 · 可逆的实现细节 · 已被既有 ADR 覆盖的事

### 格式与不可变性

- Nygard 格式：Context / Decision / Status / Consequences
- 文件名 `NNNN-kebab-case-title.md`
- **ADR 一经 Accepted MUST NOT 被修改。** 改变主意时新写一条，把旧的标记为 `Superseded by ADR-NNNN`

### 评审

单人项目阶段：作者自审，但 MUST 在 Consequences 中显式写出「我可能错在哪里」与「什么会推翻这个决定」。

## Consequences

- 触发条件是清单式的，避免「什么时候该写」成为判断题
- 不可变性意味着 ADR 目录会记录错误决策，这是有意的
- 若六个月后 ADR 数量仍在 1–5 条区间，说明触发条件定得太严，MUST 复审本 ADR
