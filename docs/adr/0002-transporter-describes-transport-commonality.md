# ADR-0002：`Transporter` 描述传输共性，而非请求/响应形状

**状态：** Accepted
**日期：** 2026-08-07
**决策者：** 项目所有者

---

## Context

`transport.Transporter` 是 Forge 中间件读取「这次调用是什么」的唯一入口。任何传输想复用框架中间件（日志、追踪、限流、metadata、selector），就必须实现它的五个方法：

```go
Kind() Kind
Endpoint() string
Operation() string
RequestHeader() Header
ReplyHeader() Header
```

这个形状是从 HTTP 与 gRPC 两个传输外推出来的。**在只有这两者时它是自洽的**：`Operation()` 就是 protobuf 方法全路径，`ReplyHeader()` 与 `RequestHeader()` 构成对称。原设计并非疏忽。

问题在引入第三种传输时才暴露 —— 接口把「恰好这两个传输共有的形状」固化成了「所有传输的形状」。

### 实测证据

2026-08-07 对 `github.com/sylphylabs/forge` 工作树全量检索 `[一手数据]`：

**一、`ReplyHeader()` 在非测试代码中零调用。**

除接口定义（`transport/transport.go:57`）与两个传输的 getter 实现外，全仓仅有测试桩引用它。传输层写响应头走的是自己的结构体字段（`transport/grpc/interceptor.go:33-34` 直接用局部 `replyHeader` 变量调 `grpc.SetHeader`），**压根不经过这个接口方法**。

即：它是死代码，却被固化为契约必填项。

**二、`Operation()` 的 13 处消费方全部只将其当作不透明字符串。**

| 消费方 | 用途 |
| --- | --- |
| `contrib/otel/tracing/tracing.go:52,68` | span 名称 |
| `contrib/polaris/ratelimit.go:39` | 限流维度 key |
| `middleware/selector/selector.go:82` | 前缀/正则/路径匹配 |
| `middleware/circuitbreaker/circuitbreaker.go:50` | 熔断分组 key |
| `middleware/logging/logging.go:33,80` | 日志字段 |
| `contrib/errortracker/sentry/sentry.go:94` | 错误上下文标签 |

**无一处解析其 protobuf 结构。** 但 `transport/transport.go:47-48` 的文档写的是 *"Service full method selector generated by protobuf"* —— **文档比实现窄**。

**三、后果已在仓库内发生。**

`contrib/transport/mcp/server.go` 与 `transport/message/server.go` 都只实现了 `transport.Server`（`Start`/`Stop` 两方法），**都未实现 `Transporter`**。因此它们拿不到任何框架中间件，各自另造了一套：

- `transport/message/message.go:104` — `Middleware func(Handler) Handler`
- `contrib/transport/mcp/server.go:22` — `MiddlewareFunc func(http.Handler) http.Handler`

这不是实现者偷懒，而是**填不出来**：消息队列没有「响应头」（消息单向，不回复）；JSON-RPC 双向流中「请求头/响应头」的划分不适用。

### 与定位的冲突

Forge 的定位是通用框架，要求「扩展点 MUST 面向『任意新传输』设计」。现状违背此约束：新传输要么谎报字段，要么放弃中间件复用。

---

## Decision

**`Transporter` 保持单一接口，但其契约改为描述传输共性，而非请求/响应形状。**

三项具体变更：

### 1. `Operation()` 重新定义为不透明标识符

文档从「protobuf 生成的服务方法全路径」改为「**标识本次调用的字符串，格式由各传输自行定义**」。

各传输的合法填法：

| 传输 | `Operation()` |
| --- | --- |
| gRPC | `/helloworld.Greeter/SayHello`（不变） |
| HTTP | 路由模板或 protobuf 方法（不变） |
| message | 消息 destination，如 `orders.created` |

**这不是放宽语义，而是让文档追上实现** —— 13 处消费方早已当不透明键使用。

消费方 MUST NOT 解析其内部结构。需要结构化信息时，用 `Kind()` 分派后读取传输自己的具体类型。

### 2. `ReplyHeader()` 移出 `Transporter`，进入可选接口

```go
// ReplyHeaderer is implemented by transports that expose a mutable reply
// header. Request/response transports do; message and stream transports
// need not.
type ReplyHeaderer interface {
    ReplyHeader() Header
}
```

消费方按需类型断言。因非测试代码零调用，此变更对现有消费方无影响。

### 3. `Kind` 明确为开放类型

`Kind` 本已是 `string` 具名类型，技术上可扩展，但仅声明了 `KindGRPC` / `KindHTTP` 两个常量，且文档未说明可否自定义。补充文档明确：**外部包 MAY 声明自己的 `Kind` 常量**，核心不维护封闭枚举。

### 被否决的方案

**拆分接口**（`Transporter` + `UnaryTransporter` + `StreamTransporter`）。否决理由：20+ 处消费方均需改为类型断言并处理「拿不到 `Operation()` 时怎么办」的分支；接口数量膨胀换来的类型精确性，在消费方只需一个不透明键的前提下没有实际收益。**为不存在的区分付出真实的复杂度。**

**维持现状。** 否决理由：直接违背通用框架定位；新传输持续各造中间件，T1 刚统一的 stream 契约对新传输无效。

---

## Consequences

### 正面

- 任何新传输实现 `Transporter` 后**自动获得**日志、追踪、recovery、限流、metadata、selector，无需重造第五套中间件契约
- 删除一个固化进契约的死方法
- 文档与实现一致，新传输实现者不再需要猜「Operation 到底能填什么」

### 负面与代价

- **`Transporter` 是公开接口，移除方法是破坏性变更。** 任何仓外实现者需删除 `ReplyHeader()` 方法或改为实现 `ReplyHeaderer`。当前尚无外部消费者（模块未公开发布），代价为零；**这也正是现在做而非以后做的理由**。
- 仓内测试桩需同步删除 `ReplyHeader()` 实现（约 6 处）。
- `Operation()` 语义放宽后，跨传输比较该字符串不再有意义。消费方若假设它总是 protobuf 路径，行为会退化 —— 已核实无此假设，但**新代码 MUST NOT 引入此假设**。

### 未解决

- `contrib/transport/mcp` 的 `MiddlewareFunc` **不在本 ADR 范围内**。它是 `func(http.Handler) http.Handler`，属 mcp-go 库边界，收敛它等于重写该适配器。本决策使 mcp *可以*实现 `Transporter`，但是否值得做需另行评估。
- `transport/message` 的私有 `Middleware`（签名带 `destination string` 一等参数）是否收敛，本 ADR 不决定。本决策只让 message 传输**能够**提供 `Transporter`，从而复用 unary/stream 中间件；其自有的 message 中间件契约是否保留，留待后续 ADR。

### 触发重新评估的条件

- 出现一个传输，其「本次调用的标识」天然不是单个字符串（如需要多维 key）
- 出现真实需求要求跨传输解析 `Operation()` 的结构
- 框架公开发布后需要再改 `Transporter`（届时破坏性变更代价不再为零）
